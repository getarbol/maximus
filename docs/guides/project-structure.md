# Project structure

This page maps a Maximus project: every file and folder `maximus prepare` reads, how each one is named,
what prepare generates in `.maximus/` and when it runs, and every refusal it makes. Look things up here;
the guides it links to explain how to write each kind of file.

## The layout

```text
notes/
├── vite.config.ts                    The configuration: maximus() states the application and its Worker
├── errors.ts                         The service's own failures
├── context.ts                        What every handler receives besides its input
├── auth.ts                           Tokens the application verifies itself
├── telemetry.ts                      Observers of every call, such as analytics
├── routes/v1/notes/[noteId].get.ts   A route: GET /api/v1/notes/{noteId}
├── mcp/tools/summarize-notes.ts      A tool only MCP serves: summarize_notes
├── mcp/instructions.md               What MCP clients read when they connect; guides and skills beside it
├── middleware/10-headers.ts          Middleware around requests or operations, in filename order
├── pages/index.ts                    A response at a fixed path outside the API: GET /
├── pages/webhooks/payments.post.ts  A provider's webhook: POST /webhooks/payments
├── crons/sweep.ts                    A scheduled handler and its schedule
├── queues/reminders.ts               The consumer of the queue named reminders
├── email/help@example.com.ts         The handler of mail to help@example.com; email/_default.ts for the rest
├── durable-objects/day-schedule.ts   A Durable Object class, exported as DaySchedule
├── index.html, app/, public/         A web app served by the same Worker
├── src/                              Your own modules: schemas, stores, domain logic
├── tests/                            Tests, which vp test runs in Node
├── .dev.vars                         Local values for vp dev, such as the development token
└── .maximus/                         Generated by prepare
```

Every entry but `vite.config.ts` is optional. Prepare reads `vite.config.ts`, the four root modules,
`index.html` and the convention folders (`routes/`, `mcp/`, `middleware/`, `pages/`, `crons/`, `queues/`,
`email/`, `durable-objects/`, `app/` and `public/`). It never reads `src/` or `tests/`: they are yours, and
the modules above import from `src/`.

Two folders are generated and ignored by Git: `.maximus/`, which prepare writes, and `.cloudflare/`, where
`vp dev` keeps the local state of the bindings (`.cloudflare/state/`) and `vp build` writes the build that
`cf deploy --prebuilt` deploys (`.cloudflare/output/v0/`).

## Configuration and root modules

`vite.config.ts` is the configuration, and `maximus()` from `@arbol-ai/vite-plugin` in its plugins states
the application and the Worker that serves it. [Configuration](../reference/configuration.md) lists every
option.

Four root modules complete the application in code. Each is optional, and each default-exports one
declaration:

| Module         | Default export           | Declares                                                                                                                                   |
| -------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `errors.ts`    | `defineErrors({ … })`    | The service's own failures. See [Errors and results](errors-and-results.md).                                                               |
| `context.ts`   | `defineContext(…)`       | What every handler receives. See [Context and middleware](middleware-and-context.md).                                                      |
| `auth.ts`      | `defineAuth({ … })`      | `resolve` for tokens the application verifies itself. See [Authentication and scopes](authentication-and-scopes.md).                       |
| `telemetry.ts` | `defineTelemetry({ … })` | Whether Maximus's diagnostics run, their observers, such as `analytics()`, and the active trace id. See [Observability](observability.md). |

A root module may end in `.ts`, `.mts`, `.js` or `.mjs`, and a project holds at most one of each name. A
root module imports no generated module at runtime, and nothing that loads only in workerd
(`cloudflare:*`, `@arbol-ai/maximus/workers`, `@arbol-ai/maximus/project`); importing their types is
fine.

## How files are named

These rules hold in every convention folder:

- A module ends in `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` or `.cjs`. Any other file, such as a
  Markdown note, is not a module.
- A file or folder whose name starts with `.` or `_` is left out: keep helpers and fixtures in
  `_shared.ts` or `_fixtures/`. `email/_default` is the one exception.
- Declarations (`*.d.ts`) and tests (`*.test.ts`, `*.spec.ts`) are left out, so a test may sit beside the
  module it tests.
- `.dev` or `.prod` before the extension restricts a module to one mode: `routes/v1/debug.get.dev.ts`
  exists in development alone (`vp dev` and `vp test`), `routes/v1/status.get.prod.ts` in builds alone. A
  mode suffix adds a module to its mode; it never replaces an unsuffixed module of the same name, and the
  two would claim one route there.
- A segment of a path is letters, digits, `_` and `-`. `index` names its folder's own path, a folder in
  parentheses such as `(admin)` groups files without adding a segment, and `[noteId]` is a parameter in
  routes and in a web app's pages.

| Folder             | A file declares                                   | Its name                                     | Example                                                         |
| ------------------ | ------------------------------------------------- | -------------------------------------------- | --------------------------------------------------------------- |
| `routes/`          | A route, `defineHandler`                          | Its path below a version, then its method    | `routes/v1/notes/[noteId].get.ts`: `GET /api/v1/notes/{noteId}` |
| `mcp/tools/`       | A tool only MCP serves, `defineTool`              | The tool, in kebab-case                      | `mcp/tools/summarize-notes.ts`: `summarize_notes`               |
| `middleware/`      | `defineMiddleware` or `defineOperationMiddleware` | Its place in the order; no dots              | `middleware/10-headers.ts`                                      |
| `pages/`           | A response handler, `HttpRoute<Env>`              | A fixed path, then its method, `GET` if none | `pages/legal/privacy.ts`: `GET /legal/privacy`                  |
| `crons/`           | A scheduled handler and `export const cron`       | Any name without dots                        | `crons/sweep.ts`                                                |
| `queues/`          | A queue consumer                                  | The queue's name, at the top level           | `queues/reminders.ts` consumes `reminders`                      |
| `email/`           | An email handler                                  | The full recipient, or `_default`            | `email/help@example.com.ts`                                     |
| `durable-objects/` | A Durable Object class                            | Kebab-case, at the top level                 | `durable-objects/day-schedule.ts`: `DaySchedule`                |
| `app/routes/`      | A page of the web app, a React component          | Its path                                     | `app/routes/notes/[noteId].tsx`: `/notes/:noteId`               |

## Routes

A route file is named `<path>.<method>.ts`, where the method is `get`, `post`, `put`, `patch` or `delete`
and the path, below `routes/`, starts with a version folder (`v1`, `v2`, …, after any groups) and names at
least one segment below it. Its default export is `defineHandler(handler, contract)`:

| File                                       | Answers                                  |
| ------------------------------------------ | ---------------------------------------- |
| `routes/v1/notes/index.get.ts`             | `GET /api/v1/notes`                      |
| `routes/v1/notes/index.post.ts`            | `POST /api/v1/notes`                     |
| `routes/v1/notes/[noteId].get.ts`          | `GET /api/v1/notes/{noteId}`             |
| `routes/v1/notes/[noteId]/archive.post.ts` | `POST /api/v1/notes/{noteId}/archive`    |
| `routes/(admin)/v1/audits.get.ts`          | `GET /api/v1/audits`                     |
| `routes/v2/notes/index.get.ts`             | `GET /api/v2/notes`                      |
| `routes/v1/debug.get.dev.ts`               | `GET /api/v1/debug`, in development only |

`/api` is the API's base path, `http.basePath` in `maximus()`. Each method of a path belongs to one file:
`notes.get.ts` and `notes/index.get.ts` claim the same route, and so do `[id].get.ts` and `[noteId].get.ts`,
since paths that differ only in a parameter's name match the same requests.

A route module default-exports its declaration and nothing else, besides types. Prepare reads its contract
to know whether the route is an MCP tool, so the contract is an object written in the call or in a `const`
of the same module, without a spread or a computed key. What a route derives from its method and path, its
operation's name and its scope among them, is in [Concepts](../concepts.md#routes-and-operations), and
every contract field in [Routes](routes.md). `bunx maximus gen route get '/v1/notes/{noteId}'` writes a route
file where it belongs.

## MCP

A file of `mcp/tools/` default-exports `defineTool(handler, contract)`: a tool only MCP serves, with no
HTTP route. Its kebab-case file name is the tool's name in snake case and the operation's in camel case:
`mcp/tools/summarize-notes.ts` is the tool `summarize_notes` and the operation `summarizeNotes`. Tool files
sit directly in `mcp/tools/`; any other module in `mcp/` must start with `_`.

The MCP server describes itself in Markdown beside them:

```text
mcp/instructions.md            What every client reads when it connects
mcp/guides/note-conventions.md A guide, served as a resource and a prompt, titled by its first # heading
mcp/skills/weekly-review.md    An Agent Skill, whose frontmatter states its description
```

Guide and skill files are named in kebab-case, 64 characters at most, and each name is the resource's: a
guide and a skill never share one, and neither is called `openapi-json` or `openapi-yaml`, the OpenAPI
document's. The Worker serves MCP at `/mcp` as soon as a route names a tool, a file of `mcp/tools/` exists
or any of this Markdown does. See [MCP](mcp.md).

## Middleware

The modules of `middleware/` run around every request or operation, in the order of their paths compared
character by character, nested folders included: number them, as in `10-headers.ts` and `20-audit.ts`. A
folder never scopes a module: every one applies to the whole service. A module default-exports
`defineMiddleware(…)`, which wraps each HTTP request before its token is verified and sees no principal, or
`defineOperationMiddleware(…)`, which runs after admission around each operation on HTTP, MCP and RPC. See
[Context and middleware](middleware-and-context.md).

## Pages

A file of `pages/` default-exports an `HttpRoute<Env>`, `(request, env, context) => Promise<Response>`,
which answers at a fixed path outside the API: `pages/index.ts` answers `/` and `pages/legal/privacy.ts`
answers `/legal/privacy`. A page answers `GET`, and `HEAD` with the head of its `GET` answer, unless its
name ends with another method, as a route's does: `pages/webhooks/payments.post.ts` answers
`POST /webhooks/payments`. Files for different methods may share a path. A method that no file of the
path declares answers `405` with `HTTP_METHOD_NOT_ALLOWED` and an `allow` header listing the ones that do,
and no page runs.

A page has no parameters, and its path may not be one the Worker answers otherwise: the API's base path
and everything below it, the health path (`/health` by default), a versioned path such as `/v1/notes`,
`/.well-known` and, when the Worker serves MCP, `/mcp`. No token admits a request to a page, so a page
holds no tenant data; that belongs to routes. A page has none of a route's other protections either: no
body limit but the one it reads with, no rate limit and no cross-origin handling. A page that browsers can
post to, such as a form, protects itself against cross-site requests.

```ts
// pages/index.ts
import type { HttpRoute } from '@arbol-ai/maximus';

/** GET /: a public page outside the API. */
const home: HttpRoute<Env> = async () =>
  new Response('Notes\n', { headers: { 'content-type': 'text/plain; charset=utf-8' } });

export default home;
```

### Receive a webhook

A provider that signs its deliveries posts them to a page named for `POST`. The page owns its
authentication completely: it reads the body with a byte limit, verifies the signature on those exact
bytes with `@arbol-ai/maximus/webhooks`, and only then treats the delivery as data. It records the
delivery and answers quickly; the work the delivery asks for belongs in a [queue consumer](background-work.md).

```ts
// pages/webhooks/payments.post.ts
import { readBodyBytes, standardErrors } from '@arbol-ai/maximus';
import type { HttpRoute } from '@arbol-ai/maximus';
import { verifyStandardWebhook } from '@arbol-ai/maximus/webhooks';

/** POST /webhooks/payments: the payment provider's signed deliveries, queued for the work they ask for. */
const payments: HttpRoute<Env> = async (request, env, context) => {
  const body = await readBodyBytes(request, { maxBytes: 64 * 1024 });
  if (!body.ok) {
    return context.fail(
      body.error.data.reason === 'too_large'
        ? standardErrors.tooLarge.create()
        : standardErrors.invalidInput.create()
    );
  }
  const verified = await verifyStandardWebhook({
    body: body.value,
    headers: request.headers,
    secret: env.PAYMENTS_WEBHOOK_SECRET,
  });
  if (!verified.ok) {
    return context.fail(standardErrors.unauthorized.create(), { 'www-authenticate': 'Signature' });
  }
  await env.PAYMENT_EVENTS.send({
    deliveryId: verified.value.id,
    body: new TextDecoder().decode(body.value),
  });
  return new Response(null, { status: 204 });
};

export default payments;
```

`maximus()` declares the secret, `PAYMENTS_WEBHOOK_SECRET: bindings.secret()`, and the queue the page
sends to, `PAYMENT_EVENTS: bindings.queue({ name: 'payment-events' })`; see [Bindings](bindings.md).
[Worker composition](worker-composition.md#verify-a-webhook) covers the three signature schemes Maximus
verifies and what a refused delivery carries.

## Background work, Durable Objects and web apps

- `crons/<name>.ts` exports its schedule as a literal, `export const cron = '*/15 * * * *'`, and
  default-exports the scheduled handler. Each distinct schedule becomes one cron trigger of the Worker.
- `queues/<queue>.ts` is named after the queue it consumes and default-exports the queue handler. The
  Worker is subscribed to the queue unless `triggers` in `maximus()` subscribes it already.
- `email/<recipient>.ts` handles mail to that exact address, and `email/_default.ts` handles the rest.
  [Background work](background-work.md) covers these three folders.
- `durable-objects/<name>.ts` default-exports a Durable Object class, which the Worker exports under the
  PascalCase of the file's name: `day-schedule.ts` is `DaySchedule`. See
  [Durable Objects](durable-objects.md).
- `index.html` at the root makes the project a web app: `app/routes/` holds its pages, `app/root.tsx` the
  layout around them and `public/` the files it serves by name. See [Web apps](web-apps.md).

Queue, email and Durable Object modules sit at the top level of their folder. Middleware, cron and queue
module names carry no dot besides a `.dev` or `.prod` suffix, so a misspelled mode such as `.local` is
refused rather than joining every mode.

## src/ and tests/

`src/` holds what your modules share: schemas, stores and domain functions, imported by relative paths
such as `../../src/notes.ts`. `tests/` holds tests, which `vp test` (`bun run test` in the starter) runs in
Node. A test calls the API as the Worker serves it through `handler` from `#maximus/http`; see
[Testing](testing.md).

## What prepare generates

Prepare writes these modules to `.maximus/`. Each starts with
`// Generated by maximus prepare (<mode>). Edit the source modules, not this file.`

| Module          | Exports or declares                                                                                                                                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `entry.ts`      | The Worker's entry, which the Worker's configuration names: everything `worker.ts` exports.                                                                                                                               |
| `worker.ts`     | The Worker: its default handler, the RPC entrypoint `Service` and each Durable Object class, serving the application, MCP when the project serves it, the pages, the cron, queue and email modules and a web app's build. |
| `app.ts`        | `app`: the application with every route and tool bound to the base, checked to run the project's operation middleware. Its `operations` type a web app's calls.                                                           |
| `http.ts`       | `handler`: the API as the Worker serves it, below its base path, behind its request middleware and with MCP when served, without the Workers runtime. Tests call it in Node.                                              |
| `env.d.ts`      | The global `Env`, inferred from the bindings of both modes by `cf/config`'s `InferEnv`. A binding to one of the Worker's own Durable Object classes is typed by that class.                                               |
| `register.d.ts` | The global `MaximusRegister`: the base, the error catalog of `errors.ts` and `Env`, which type every `defineHandler`, `defineTool` and `defineContext`.                                                                   |
| `config.ts`     | `application` and `worker`: what `vite.config.ts` states, as data the Worker carries.                                                                                                                                     |
| `base.ts`       | `base`: the application, completed by `errors.ts`, `auth.ts`, `context.ts`, `telemetry.ts`, the MCP Markdown and the operation middleware.                                                                                |
| `middleware.ts` | `middleware` and `requestMiddleware`: the modules of `middleware/` in their order, split by phase.                                                                                                                        |
| `mcp.ts`        | `mcp`: the instructions, guides and skills of `mcp/`, when any exists.                                                                                                                                                    |
| `app-routes.ts` | `routes`: React Router's routes for the pages of `app/routes/`, in the layout of `app/root.tsx` when there is one; for a web app with pages.                                                                              |

The starter's `package.json` maps `#maximus/*` to `./.maximus/*.ts`, so any module imports
`#maximus/http` or `#maximus/app-routes` whatever its depth, and its `tsconfig.json` includes
`.maximus/*.ts`. Prepare rewrites only the modules whose text changed and removes `mcp.ts` and
`app-routes.ts` once nothing produces them. Never edit `.maximus/`, and never commit it: the starter's
`.gitignore` lists it.

Preparing reads your modules without running them, and changes nothing outside `.maximus/`: it creates no
Cloudflare resource and applies no migration.

## When prepare runs

| When                     | Mode                                  | What happens                                                                                                          |
| ------------------------ | ------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `vp dev`                 | `development`                         | When the server starts, and again whenever a file prepare reads is added, changed or removed.                         |
| `vp build`, `vp preview` | `production`                          | Before the build, whatever Vite's `--mode`.                                                                           |
| `vp test`                | `development`                         | When the tests start, so the API accepts the development token from `localhost`.                                      |
| `maximus prepare`        | `production`, or `--mode development` | On demand. The starter runs it as its `prepare` script, after `bun install`, and before `tsc` in `bun run typecheck`. |

The mode decides what the Worker holds. Only `development` declares the development token's binding and the
policy that accepts it, includes `.dev` modules and lets a web app reach Vite's modules; `production`
includes `.prod` modules instead. Every build is a production build, so nothing that exists for development
reaches a deployed Worker.

Under `vp dev`, a change reaches the running Worker in one of three ways:

- An edit inside a module updates that module.
- A file that changes `.maximus/`, such as a new route, reloads the page.
- A change to the Worker itself restarts the server: `index.html` added or removed, a Durable Object
  module added or removed, a cron or queue module added or removed, or a schedule changed.

A change to `vite.config.ts` restarts the server too.

## What prepare refuses

A refusal stops prepare before it writes anything: `.maximus/` keeps what it held, and the message names
the file. It stops `vp build` and a starting `vp dev`; once the server runs, it appears as Vite's error
until the file is fixed. `maximus prepare` prints it as `maximus: <message>` and exits with 1.

### Symlinks

Prepare reads nothing through a link, which could pull code from outside the project, and writes nothing
through one.

| Message                                                 | Refuses                                                                                               |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `Project directory cannot be a symlink: <folder>`       | A convention folder, `app/`, `app/routes/`, `public/`, `mcp/guides/` or `mcp/skills/` that is a link. |
| `Project modules cannot be symlinks: <file>`            | A link inside a convention folder.                                                                    |
| `The <name> module cannot be a symlink.`                | `errors`, `auth`, `context`, `telemetry` or `app/root` as a link.                                     |
| `MCP Markdown must be an ordinary file: <path>`         | `mcp/instructions.md`, a guide or a skill that is a link or a folder.                                 |
| `Public files cannot be symlinks: <path>`               | A link in `public/`.                                                                                  |
| `The generated .maximus directory cannot be a symlink.` | `.maximus/` itself as a link.                                                                         |
| `Generated files must be ordinary files: <name>`        | A file of `.maximus/` replaced by a link or a folder.                                                 |

### Names

| Message                                                                                                                                      | Refuses                                                                                                                                                                                                         |
| -------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Name a route file by its method, such as routes/v1/tasks/index.get.ts: <file>`                                                              | A route file without a method suffix, or with `head` or another unknown one.                                                                                                                                    |
| `Operation file must live below routes/v1/ (or another version): <path>`                                                                     | A route outside a version folder, or the version folder's own `index`.                                                                                                                                          |
| `Unsupported routes segment: <segment>. Pages use fixed paths; operations and app pages support [parameter].`                                | A segment that is neither a name nor `[parameter]`, such as `[...rest]` or `my.notes`. For a page the message names `pages` or `app`; a parameter in `pages/` and a page named for `HEAD` are refused this way. |
| `MCP modules are kebab-case tools directly in mcp/tools/, such as mcp/tools/summarize-tasks.ts: <file>`                                      | A module of `mcp/` outside `mcp/tools/`, nested below it, or not in kebab-case.                                                                                                                                 |
| `Name MCP Markdown in kebab-case, at most 64 characters: <path>`                                                                             | A guide or skill file named otherwise.                                                                                                                                                                          |
| `MCP resource name <name> is taken: guides and skills need names of their own, and openapi-json and openapi-yaml name the OpenAPI document.` | A guide and a skill with one name, or either named `openapi-json` or `openapi-yaml`.                                                                                                                            |
| `Name a module without dots but its mode suffix, .dev or .prod: <file>`                                                                      | A middleware, cron or queue module such as `crons/debug.local.ts`.                                                                                                                                              |
| `Name an email module after the recipient it handles, such as help@example.com, or _default: <file>`                                         | An email module no message would reach, such as `email/support.ts`.                                                                                                                                             |
| `queues modules require distinct top-level names: <name>`                                                                                    | A queue module in a subfolder, or two with one name and different extensions. The same message for `email`.                                                                                                     |
| `Durable Object filenames must be top-level kebab-case names: <name>`                                                                        | `durable-objects/SessionStore.ts` or a module in a subfolder.                                                                                                                                                   |
| `Duplicate Worker export: <Class>`                                                                                                           | Two Durable Object modules with one name, or `durable-objects/service.ts`, since `Service` is the RPC entrypoint.                                                                                               |
| `Keep at most one <name> module: <file> or <file>.`                                                                                          | `errors.ts` beside `errors.mjs`, for instance, or two `app/root` modules.                                                                                                                                       |
| `Name public files with letters, digits, dots, underscores, tildes and hyphens: <path>`                                                      | A web app's public file such as `public/my logo.png`.                                                                                                                                                           |

### Paths

| Message                                                                                                               | Refuses                                                                                                                                                 |
| --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Multiple route files claim <METHOD> <path>: <file> and <file>.`                                                      | Two files for one method and path, including paths that differ only in a parameter's name.                                                              |
| `<file>: Path parameter names must be unique and safe: <path>`                                                        | A route whose path names one parameter twice, or a parameter called `constructor` or `prototype`.                                                       |
| `Multiple page files claim <METHOD> <path>: <file> and <file>.`                                                       | Two files of `pages/` for one method and path: `pages/about.ts` beside `pages/about/index.ts` or `pages/about.get.ts`.                                  |
| `Page path is reserved or malformed: <path>. Move the API with http.basePath.`                                        | A page at a path the Worker answers otherwise, as listed under [Pages](#pages).                                                                         |
| `Multiple page files claim <path>: <file> and <file>.`                                                                | Two pages of `app/routes/` for one path, parameter names aside.                                                                                         |
| `The page <path> claims a path the API, discovery, MCP, the build's assets or pages/ answer: move it in app/routes/.` | A page of the web app at or below the API's base path, `/.well-known`, `/mcp` or `/assets`, at the health path, a versioned path or a path of `pages/`. |
| `A web app answers at the root: keep the API below http.basePath, /api by default.`                                   | A web app whose API's base path is `/`.                                                                                                                 |
| `app/routes/ holds the pages of a web app: add its index.html at the project root.`                                   | `app/routes/` without `index.html`.                                                                                                                     |

### Module contents

| Message                                                                                                                                                       | Refuses                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `Cannot discover <file>: <what the parser found>`                                                                                                             | A module that does not parse.                                                                                                       |
| `<file> must default-export its defineHandler declaration and nothing else. Keep helpers private or in _files.`                                               | A route module with another export besides types, `export *`, or no default export. The same message names `defineTool` for a tool. |
| `<file> must write its defineHandler contract as an object, in the call or in a const of the module: prepare reads from it whether the route is an MCP tool.` | A contract built with a spread, a computed key, an import or a `let`.                                                               |
| `Runtime import <source> creates a generated-module cycle in <file>. Use a type-only import or shared domain module.`                                         | An import of a generated module that imports this one, by the table below.                                                          |
| `Configuration must remain importable outside workerd: <source> in <file>. Import its types only.`                                                            | A root module that imports `cloudflare:*`, `@arbol-ai/maximus/workers` or `@arbol-ai/maximus/project` at runtime.                   |
| `Start the guide with its # title: <path>`                                                                                                                    | A guide whose first line is not a `#` heading.                                                                                      |
| `Start the skill with frontmatter, ---, description: …, ---: <path>`                                                                                          | A skill without frontmatter.                                                                                                        |
| `State the skill's one-line description in its frontmatter: <path>`                                                                                           | A skill whose frontmatter has no description.                                                                                       |
| `A skill's frontmatter states its one-line description, and its name only as its file does: <path>`                                                           | Any other frontmatter key, or a `name` its file does not have.                                                                      |

A generated module imports your modules, so importing it back at runtime would form a cycle. An
`import type` or `export type` is always allowed; `import { type app }` is not, since under
`verbatimModuleSyntax` it still loads its module:

| Module                                                      | Never imports at runtime from `.maximus/` or `#maximus/` |
| ----------------------------------------------------------- | -------------------------------------------------------- |
| `errors.ts`, `auth.ts`, `context.ts`, `telemetry.ts`        | Any generated module                                     |
| `middleware/`                                               | `base`, `middleware`, `app`, `http`, `worker`, `entry`   |
| `routes/`, `mcp/tools/`                                     | `app`, `http`, `worker`, `entry`                         |
| `pages/`, `crons/`, `queues/`, `email/`, `durable-objects/` | `worker`, `entry`                                        |

### When the Worker is configured

`vp dev`, `vp build` and `vp test` also refuse what makes no Worker: a cron module whose schedule is not a
string literal, a leftover `maximus.config.ts` or `cloudflare.config.ts`, and a web app whose Vite `base` or
`build.assetsDir` would move its build. [Configuration](../reference/configuration.md#refusals) quotes each
message. What breaks a rule of the application itself, such as an MCP route without a description, is
refused when the Worker starts, with a `TypeError` that names the rule.
